# Feature Specification: Telegram 语音消息识别

**Feature Branch**: `001-telegram-voice-transcription`

**Created**: 2026-10-19

**Status**: Draft

**Input**: User description: "telegram 端把用户发来的语音转成文字再回复"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 说一句就能聊 (Priority: P1)

用户在 Telegram 里按住说话、发出一条语音，助手像收到文字一样理解这段话并正常回复，用户无需再打字复述。

**Why this priority**: 这是整个特性的存在理由。没有它，语音消息会被静默忽略——用户以为助手听见了，实际什么回应也没有。单独交付这一条就已经有完整价值：语音消息从"被丢弃"变成"能对话"。

**Independent Test**: 在真实 Telegram 会话里发送一条语音（如"今天晚上想吃什么"），确认助手给出与语音内容相符的回复，且该条消息在当前时间线里以转写后的文字形式存在、可被后续轮次引用。

**Acceptance Scenarios**:

1. **Given** 用户与助手的会话空闲，**When** 用户发送一条内容清晰的语音，**Then** 助手在可接受的等待时间内给出针对该内容的回复。
2. **Given** 用户发送语音，**When** 助手回复后用户接着发文字继续同一话题，**Then** 助手表现出把前一条语音内容当作对话上下文（话题连续）。
3. **Given** 语音内容包含值得长期记住的信息（如"我对花生过敏"），**When** 该轮结束，**Then** 助手像收到同内容的文字一样把它当作可记忆的候选信息。

---

### User Story 2 - 听不清就像人一样说一句 (Priority: P2)

语音模糊、听不清时，助手用自然的话回应——就像真人没听清会开口让对方重说一样。回复什么内容由模型结合当下对话自行组织，不是仓库里写死的固定话术。转写能力本身不可用则不属于这条：那是系统故障，走后台错误路径，不伪装成"没听清"。

**Why this priority**: 人与人互动时，听不清的一方一定会说"你刚说啥？"，这条保证助手不"装听不见"。同时把"能力不可用"划归程序故障，避免用一句面向用户的话术把缺陷盖过去——那是开发者要修的问题，不是用户的错。

**Independent Test**: 用一段没有人声的音频触发"听不清"，确认助手给出的是自然生成的一句话（多次触发措辞不完全相同）；再制造能力不可用，确认走的是错误路径（产生可供开发者定位的错误记录、进入既有故障处理），且没有向用户输出"没听清"之类的伪装文案。

**Acceptance Scenarios**:

1. **Given** 转写能力正常，**When** 用户语音里没有说话声或完全听不清，**Then** 助手用自然语言反馈没听清/没明白，并可邀请用户重说或改用文字。
2. **Given** 上述反馈由模型结合当轮对话生成，**When** 连续多次遇到听不清，**Then** 措辞随情境变化（体现为自然生成，而非固定模板复读）。
3. **Given** 转写能力不可用（未启用 / 服务不可达 / 内部错误），**When** 用户发送语音，**Then** 该轮按系统故障处理：产生可供开发者定位的错误记录并进入既有故障处理/重试路径，MUST NOT 以"没听清"等面向用户的话术掩盖。
4. **Given** 发生上述任一情形，**When** 该轮结束，**Then** 助手不会基于猜测的内容编造回复，也不会向用户暴露技术细节（服务名、错误码、堆栈）。

---

### User Story 3 - 连续说也不掉链子 (Priority: P3)

用户连续发多条语音、或在助手还在回复时又补一条语音，这些消息按顺序并入同一轮对话，不丢、不重复、不互相打架。

**Why this priority**: 真实聊天是连珠炮式的。P1/P2 证明了"单条语音能通"，这一条保证"连着说"也不会乱序或丢失。它可以在 P1 之上单独验证：连发两条语音，观察回复是否覆盖两条内容。

**Independent Test**: 快速连发两条内容相关的语音（如"我明天要出差" + "大概去三天"），确认助手一次回复中同时考虑到两条，且时间线里两条都按发送顺序存在。

**Acceptance Scenarios**:

1. **Given** 会话空闲，**When** 用户连续发送两条语音，**Then** 两条都按发送顺序进入上下文，助手不漏答其中任一条。
2. **Given** 助手正在回复上一轮，**When** 用户又发来一条语音，**Then** 该语音在转写完成后与文字消息一样并入正在进行的这一轮，助手能接着应答。
3. **Given** 同一条语音被通道重复投递，**When** 系统处理，**Then** 用户只收到一次回复，时间线里该语音只出现一次。

---

### Edge Cases

- 语音消息同时带文字说明（如用户发送音频文件时附了 caption）：文字说明与转写内容共同构成该条消息，文字说明在前（FR-012）。
- 语音过长（例如数分钟）或体积过大：超出 FR-003 范围时由助手自然告知无法处理，不静默丢弃。
- 语音内容是外语或方言：按原语言转写，不做翻译。
- 语音里出现多个说话人（环境噪音/旁人插话）：属"听不清"范畴，按 FR-005 由助手自然反馈，不硬猜内容。
- 转写耗时明显长于文字消息：沿用既有的"正在处理"状态反馈，不新增面向用户的专门文案。
- 转写结果为空字符串或仅剩标点：判定为"没听清"（FR-004），按 FR-005 反馈；但若听出了简短而有意义的应答（如"嗯""好"），按正常转写处理，交给模型理解。
- 转写能力不可用：按 FR-013 走系统故障路径，不产生面向用户的对话回复。
- 用户发送的是 Telegram 的其他非文本类型（图片、贴纸、文件、视频）：本次保持不变（贴纸仍走既有占位描述，其余仍忽略）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接收用户在 Telegram 会话中发送的语音消息，不再将其静默丢弃。
- **FR-002**: 系统 MUST 把语音内容转成文字，并把该文字作为本条用户消息的内容进入既有对话流程（与用户直接打字的处理无差别）。
- **FR-003**: 系统 MUST 对语音设定可处理范围（按类型与时长/体积上限），超范围时按 FR-005 让助手自然告知无法处理，而不是长时间无响应。
- **FR-004**: 系统 MUST 在转写结果不可用（听不清、结果为空/无意义、识别置信度过低）时判定该条消息为"没听清"，MUST NOT 以猜测内容继续生成回复。
- **FR-005**: 转写结果为"没听清"时，面向用户的回应 MUST 由模型结合当轮对话自然生成（像人一样表达没听清/没明白，可邀请重说或改用文字），MUST NOT 使用仓库内置的固定话术。
- **FR-006**: 转写能力整体不可用（未配置、服务不可达、内部错误）MUST 被视为系统故障，按 FR-013 处理，MUST NOT 表现为面向用户的对话反馈。
- **FR-007**: 系统 MUST 保证同一用户的语音消息按发送顺序处理，连续多条语音不漏、不重复。
- **FR-008**: 用户 MUST 能够通过再次发送语音或改用文字来继续对话，不需要任何额外授权、开关或初始化操作。
- **FR-009**: 系统 MUST 保留"本条消息源自语音"这一事实，使下游（如助手的自我表述、运维排查）能区分语音与文字来源。
- **FR-010**: 转写成功后 MUST 静默理解：系统 MUST NOT 把识别出的文字回显给用户，该文字即本条用户消息的内容，进入既有对话流程。
- **FR-011**: 任何面向用户的文本 MUST NOT 暴露技术细节（服务名、错误码、内部堆栈、文件路径）。
- **FR-012**: 系统 MUST 处理语音消息与文字说明并存的情形（如音频文件带 caption），并 MUST 保留文字说明，不得因转写而覆盖或丢弃它。
- **FR-013**: 转写能力不可用 MUST 作为系统级故障处理：产生可供开发者定位的错误记录，并进入既有故障处理/重试路径。开发侧 MUST 将其作为缺陷修复；若属预期状态（能力可能未启用），MUST 让能力具备明确的可用性判定（启动即可知、可自检），MUST NOT 表现为随机不可用。

### Key Entities *(include if data involved)*

- **入站语音消息**：用户发出的一条语音（或音频文件），关键属性为来源类型、时长、体积、发送时刻、所属会话。
- **转写文本**：由语音内容得到的文字，是这条用户消息在对话时间线中的实际内容；可能为空（视为不可用）。
- **会话时间线条目**：既有概念。本特性只改变"用户消息的内容来源"，不改变其角色、顺序与在记忆沉淀中的处理方式。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户发送一条日常短语音（30 秒以内、内容清晰）后，助手在不晚于同长度文字消息两倍的时间内给出回复。
- **SC-002**: 被静默忽略的语音消息占比从当前 100% 降到 0%——每条语音要么得到回复，要么得到助手自然的"没听清"反馈，要么进入系统故障路径（可被开发者定位）。
- **SC-003**: 对同一内容的"语音输入"与"文字输入"，助手回复的主题一致率达到抽样 90% 以上（抽 20 组对照）。判定口径：同一组内，语音轮与文字轮各自的助手回复，**核心意图一致**即计为一致——具体指回答所针对的对象/动作与原话题相符（如问"晚上吃什么"，两轮都在讨论吃饭安排）；只要都在同一话题域内即为一致，不要求措辞相同、不要求信息量相同；出现话题偏离、答非所问，或把语音内容整体理解成另一件事，计为不一致。20 组中一致数 ≥ 18 组视为达标。
- **SC-004**: "听不清"的样本中，100% 得到一句自然生成的回应（抽样中措辞不重复模板），0% 出现基于猜测内容的编造回复。
- **SC-005**: 连续发送两条语音时，100% 的样本两条内容都被纳入该轮回复（无漏答）。
- **SC-006**: 能力不可用的样本中，100% 产生可供开发者定位的错误记录，0% 出现伪装成"没听清"的面向用户文案。

## Assumptions

- 转写能力由本机既有的媒体能力面提供（与出图/合成语音同一来源），或等价的本地/可配置服务；具体选型属于实现阶段决策，本规格不作限定。
- v1 只覆盖 Telegram 的语音留言与音频文件；圆视频留言与其他非文本类型不在本次范围内，保持既有行为。
- 用户主要使用中文，系统按原语言转写，不做翻译。
- 单条语音时长通常在 1 分钟以内；超长语音的取舍在实现阶段按 FR-003 的上限确定。
- 转写后的文字进入既有时间线，后续轮次与记忆沉淀对它与文字输入一视同仁。
- 用户无需任何额外开关或授权即可使用；也不需要用户在发送前声明"我要发语音"。
- 转写能力不可用时沿用既有的失败轮次重试机制处理瞬时/持久故障，不新增用户可见的重试交互；相关错误记录并入既有错误日志（FR-013）。
- 等待转写期间沿用既有的"正在处理"状态反馈，不新增"正在听"之类专门文案。
- "没听清"的措辞由模型生成，因此随上下文变化；仓库内 MUST NOT 内置固定话术（FR-005）。
- 语音消息同时带文字说明时，文字说明在前、转写结果在后，共同构成该条用户消息的内容（FR-012）。

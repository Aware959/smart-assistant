## 6. P1 · 记忆对用户完全不可见

### 现象

LLM 在替用户写永久断言，用户既看不到也无法纠正。

### 现状（2026-10-20 核对）

`backend/src/api/` 仍然只有两个路由（`api/chat.rs:20-25`）：

```rust
.route("/chat/stream", post(handle_chat_stream))
.route("/ws", get(handle_ws))
```

**没有任何记忆的查询 / 编辑 / 删除接口**，前端也没有记忆页。库里此刻躺着 6 条未过期记忆，
用户既无法确认它记了什么，也无法删掉一条错的——2026-10-20 清理的那 3 条脏记忆，
还是靠人肉连库删掉的。

这仍是「记忆感觉伪」的最大来源：不是它记错了，而是这一切**无法验证**。

> 注：写入侧已收窄（见归档 §2），准入质量比 2026-09 好，但「可见性」这一半没变。

### 待决策

- [ ] 是否做记忆管理接口 + 前端页（`GET /memories`、`PATCH`、`DELETE /memories/:id`）。
- [ ] 若做，是否需要「低置信度记忆待确认」机制（LLM 标记 → 用户确认 → 转正）。
- [ ] 优先级：写入侧已达标（归档 §2、§4），可以开始考虑这一项了。
- [ ] 注意：`src/api/**` 与前端当前不在开发主线（见 `AGENTS.md`），动之前需要用户点名。

## 8. P2 · 出站投递：已有「失败轮次重试」，但仍不是 outbox

### 现状（2026-10-20 核对）

入站方向有保障（游标先落盘再处理，崩溃重启续传）。出站方向**已比 2026-09 好**：
`pending_retry` 表 + 启动/周期扫表重试（提交 `c15a080`）接管了「整轮失败或超时且零投递」的情况，
队列在 DB 里，进程重启不丢。

仍未覆盖的：

- **进程崩溃瞬间在途的那一条仍会丢**：入队发生在「判定失败之后」，崩溃来不及入队。
- **只有 Telegram 接了扫表重试**，iLink 没有（`channels/ilink/` 无对应路径）。
- **重试单位是「整轮对话」，不是「单条出站消息」**：一次回复被拆成多条时，
  没有 per-message 的幂等键，重投可能重复发。

### 待决策

- [ ] 是否做 `pending_sends`（消息级 outbox + 启动重投 + 幂等键）。
      代价：新增 schema、启动时序、幂等键设计。
- [ ] 若做，是否同时给 iLink 接上同一套。
- [ ] 顺序建议：先看崩溃丢消息的实际频率，再决定值不值得做。

## 9. P2 · iLink 主动推送失败会烧掉用户的 context_token

### 证据

`channels/ilink/push.rs:91`：`Err` 分支执行 `entry.contacts.remove(external_id)`，
**直接丢弃该用户的 token**，导致窗口内无法再主动推送。

发送本身已有重试（`channels/ilink/protocol.rs:388` 用 `with_send_retry("ilink/sendmessage", SEND_RETRY, …)`），
所以这只会发生在 5 次尝试全败之后（比原来一次即丢好很多），但重试耗尽仍会烧窗口。

### 待决策

- [ ] 改为「连续失败 N 次才丢」，而非一次即丢。
- [ ] 或区分失败原因：网络类失败不丢，`context_token 已过窗口` 才丢。
- [ ] 注意：iLink 端当前不在开发主线（见 `AGENTS.md`），动之前需要用户点名。

## 已解决（归档）

| 原编号 | 问题 | 解决方式与落点 |
|---|---|---|
| §1 | 记忆召回阈值单位是 L2 距离，命名误导 | 向量表度量显式声明为 `cosine`（`db/vec.rs:23`、建表 `distance_metric=cosine`）；配置改名 `MEMORY_RECALL_MIN_SIMILARITY`，默认 **0.79**，注释写明「最低余弦相似度」（`config.rs`、`.env.example:60`）。**召回不再每轮注入**——改成模型按需调 `recall_memory`（`llm/tool.rs:259`、`core/context/prompt.rs:82`），「每轮塞 5 条噪声」的现象随之消失 |
| §2 | `memories` 表范围过宽，把「对助手的指令」当「关于用户的事实」 | 写入入口改为 `MemoryKind` 白名单（trait / preference / routine / plan，`db/memory.rs`）+ `remember` 工具的**三道准入闸**，第一条即「是关于用户本人的处境、偏好、经历或约定，**不是关于你该怎么回话**」（`llm/tool.rs:293-310`）。产生该问题的单条消息抽取旁路整体删除。存量 3 条脏记忆已于 2026-10-20 手删（见附录 A） |
| §3 | 事实化 prompt 的归一化规则产出损坏文本（「对方希望对方…」） | 产出该文本的 `user_memory_extraction.rs` / `MEMORY_SUMMARY_PROMPT` 链路已整体删除；库中那条已由模型用 `supersedes` 改写为「对方希望 AI 在想念对方的时候能大胆说出来，不要藏着。」（该条本身已按 §2 的判据于 2026-10-20 删除） |
| §4 | 记忆内容质量：元评论、无指代、问句当事实 | 写入改为模型在工具循环里发起，**看得见上下文**，「那个任务」这类指代能当场消解；工具描述明确禁止「问句」「他自称…这类转述」「悬空指代」，并要求「忘了它就会让你答错或只能泛泛而谈」（`llm/tool.rs:303-307`）。判据不再是单条消息旁路里的 `is_memory` |
| §5 | 去重阈值过松，同一事实存多遍 | `MEMORY_DEDUP_MIN_SIMILARITY` 默认 **0.92**（相似度语义，`.env.example:64`）；去重的主要手段改为模型显式 `supersedes` 原地改写，阈值只作兜底 |
| §7 | `settle_memory` 耦合在「发送成功」之后 | `settle_memory` 已整体移除；记忆由 `remember` 工具在工具循环内**即时**写入（`llm/tool.rs:421`），与出站投递成功与否无关，发送失败不再丢记忆 |

### 归档时的两点说明

- **§5 的子项没按原建议做**：「语义相同但 tier/TTL 不同时保留信息量更大的那条」未实现——
  现在是模型给的新说法直接覆盖旧行（`db/memory.rs` 的 `revise`）。这是有意的设计选择：
  新说法带有当前上下文，比旧的更可信。
- **§2 的「memories 与 self_profile 直接冲突」症状已消失**，但主要不是靠清理记忆，
  而是 `self_profile` 本身改成了「女朋友」人设（`身份定位 = 对方的女朋友`、`相处姿态 = 女朋友`）。
  两条角色类记忆 2026-10-20 已删。
- **仍未做（不是遗漏）**：`self_profile` 的「自动演进」通道（LLM 提案 → 人确认 → 生效）。
  它是独立功能，与「记忆准入」不是一回事，是否要做仍未决定——原 §2 最后一条待决策转入此处挂着。

## 附录 B · 复现方式

诊断脚本（只读，不改库）在 `%TEMP%\opencode\`：

| 脚本 | 用途 |
|---|---|
| `memdiag.py` | 记忆全文、分布、过期统计 |

> 换未归一化输出的 embedding 模型，本文档里 L2↔余弦的换算需重测。

## 0. 阅读指引

优先级按「对用户体验的影响 × 修复成本」排定：

| 级别 | 含义 |
|---|---|
| P0 | 正在持续产生错误行为，且用户可感知 |
| P1 | 能力缺失或数据不可信，尚未直接破坏体验 |
| P2 | 已知技术债，无近期症状 |

「已决策」小节记录用户已明确表态的项（含「暂不动」），**不要重复讨论**。

## 1. P0 · 记忆召回阈值：单位是 L2 距离，不是余弦相似度

### 现象

记忆每轮都在注入，但注入内容基本与当前话题无关。表现为模型偶尔前言不搭后语、
把不相干的事硬联系起来。

### 证据

`MEMORY_RECALL_THRESHOLD=0.9`，直觉读作「九成相似」，实际是「距离小于 0.9」。

- 过滤发生在 `backend/src/core/memory/mod.rs:251`：`distance <= threshold`
- 距离来自 vec0 的 `v.distance`（`backend/src/db/memory.rs:189`，`ORDER BY v.distance`）
- 建表未指定度量（`backend/src/db/vec.rs:145`：`USING vec0(memory_id TEXT PRIMARY KEY, embedding FLOAT[768])`），
  vec0 默认 **L2**
- `text-embedding-embeddinggemma-300m` 输出**已归一化**（实测模长 1.0000）

对已归一化向量：`d = sqrt(2 - 2·cos)`，于是

```
0.9 阈值  等价于  cos ≥ 0.595
```

实测 20 条真实用户消息 × 8 条未过期记忆，在不同阈值下的平均注入条数（k 上限 5）：

| 阈值(L2) | 等价余弦 | 平均注入 |
|---|---|---|
| **0.90（现状）** | cos≥0.595 | **4.7 条** |
| 0.80 | cos≥0.680 | 1.4 条 |
| 0.70 | cos≥0.755 | 0.4 条 |
| 0.65 | cos≥0.789 | 0.2 条 |

现状等于**每轮把记忆库里 5 条塞进 prompt**，其中绝大多数无关。实际注入样例：

```
用户：书店怎么知道？它又不是人类
  cos=0.657  对方自称只是傲娇
  cos=0.623  对方提到的那个任务还没确定，估计还得讨论
  cos=0.602  对方本身是内向话少的人
  cos=0.584  对方会一点厨艺
  cos=0.580  用户称助手为其女朋友，暗示双方存在恋爱关系或角色设定
```

真正相关的配对（「我本身就是内向话少的」↔「对方本身是内向话少的人」）cos=0.886，
噪声区间 0.60–0.73。**0.65–0.70 能干净切开这两组。**

这比「没有记忆」更糟：唯一的真相关项被 4 条噪声淹没，模型还会强行关联噪声。

### 附带问题：配置项命名误导

`memory_recall_threshold` 读起来像相似度阈值，实际是距离阈值。`.env` 注释写「调大=更宽松」，
语义正确但容易误设。建议在 `.env.example` 与 config 注释里**显式写明单位是 L2 距离**，
或直接改名为 `memory_recall_max_distance`。

### 待决策

- [ ] 阈值取值。**建议 0.65**（实测能分开相关/噪声两簇，且保留 `cos≥0.789`）。
      0.70 更保守、召回更少；0.80 折中。
- [ ] 顺手把单位写进 `.env.example` 与 `backend/src/config.rs` 注释（改动极小，建议同批做）。
- [ ] 是否需要按 `memory_type` 差异化阈值（`fact` 该更严、`preference` 可更松）。
      暂不建议：先跑一段时间单一阈值看效果。

## 2. P0 · `memories` 表范围过宽：把「对助手的指令」当「关于用户的事实」存

### 现象

`memories` 里混入了角色设定类内容，与 `self_profile` 的人格定义直接冲突，
且两条通道在 prompt 里互相矛盾。

### 证据

当前库里这两条（`tier=core`）：

```
[personal]   用户称助手为其女朋友，暗示双方存在恋爱关系或角色设定。
[preference] 对方希望AI扮演其女朋友的角色，并希望AI使用"宝宝"、"宝贝"、"老公"等称谓来称呼对方。
```

而 `self_profile` 里**已经有**这一类内容，且写在最高优先级：

```
身份定位   陪伴型对话伙伴，不是客服也不是人生导师
相处姿态   平等同伴
禁用词     首先其次最后、作为AI、很高兴为您服务、请您…
边界       不追问隐私，不想说就停
```

21 行、条条互不矛盾。memories 那两条与 `身份定位`/`相处姿态` **直接冲突**
（女朋友+「老公」称呼 ≠ 平等同伴），且两条互为重复（cos 0.756）。

prompt 层面的矛盾（`backend/src/core/context/prompt.rs`）：

| 位置 | 内容 |
|---|---|
| `persona_block:11`（开头，最高优先级） | 你的身份**只能**来自「我是谁（AI 自己）」；`never call yourself an AI` |
| `system_prompt:55` | `Your identity comes ONLY from 我是谁` |
| `recall_block:82`（结尾） | 以下全是**关于对方**的事实…**绝不是你自己的属性** |

于是模型同时收到：身份只来自 self_profile / 身份是平等同伴 /
扮演女朋友叫我老公且这是「关于对方的事实、与你无关」。

**一条关于助手行为的指令，被 recall 通道打上「与助手无关」的标签送进来。
无论采信哪边都是错的。**

### 根因：抽取判据在入口处没设防

`backend/src/core/memory/user_memory_extraction.rs:309`：

> is_memory: TRUE only when the message carries substantive information worth
> recalling later (personal info, **preferences**, important experiences, plans, task progress)

「你当我女朋友、叫我宝宝」在语义上**就是一个 preference**。判据只挡闲聊和提问，
挡不住对助手的指令。

### 为什么当初会这样（推测，未验证）

`self_profile` 是纯人工维护，改一次要手动；而「关系会演进」是真实需求。
于是想让 LLM 自动学 —— 但 `preference` 这个类目既是入口也是破口。
**这是把 profile 演进塞进了 memory，典型的 scope creep。**

### 待决策

- [ ] **收窄 `memories` 定义为「关于用户的事实」**，助手侧一切（人格/身份/称呼/边界/语气）
      只走 `self_profile`。
- [ ] 判据加排除项：`is_memory` 明确写
      `FALSE for instructions about how the assistant should behave — role, persona, tone,
      form of address, boundaries`。
- [ ] 是否新增 `kind` 枚举把 `instruction` 单独分出来（不落 memories），
      还是仅靠 prompt 排除、schema 不动。**建议先只改 prompt**，观察一段时间。
- [ ] 存量 2 条角色类记忆如何处置：**删除**，或手工写进 `self_profile`
      （如新增 `关系定位` 键，与 `身份定位`/`相处姿态` 并列）。
- [ ] 更根本的问题：`self_profile` 是否需要一个「自动演进」通道
      （LLM 提取提案 → 人工确认 → 生效并留可撤销记录）。
      **这是独立功能，不属于 memories 职责。是否要做，尚未决定。**

## 3. P0 · 事实化 prompt 的归一化规则产出损坏文本

### 现象

`memories` 中出现语义不通的条目。

### 证据

```
对方希望对方在想自己时就大方地说出来。
```

`backend/src/core/memory/user_memory_extraction.rs:337` 强制「主语必须是对方」，
但**未处理「宾语也是听者」**的情况，于是产出「对方希望对方…」。

该规则隐含假设「记忆里只有关于用户的事实」——一旦按第 2 项混入对助手的指令，
这条规则就会崩。这也是两问题的耦合点。

### 待决策

- [ ] 在 `MEMORY_SUMMARY_PROMPT` 加负例，禁止产出「对方希望对方…」这类双对方句式。
- [ ] 顺带禁掉元框架短语（见第 4 项）。
- [ ] 归一化规则是否应放宽为「主语用对方，宾语按原意保留」？**建议放宽**，
      比堆负例更根本。

## 4. P1 · 记忆内容质量：元评论、无指代、问句当事实

### 现象

11 条记忆里真正可用的约 3 条。

### 证据

156 条用户消息沉淀出 11 条（提取率 7%），逐条看：

| 内容 | 问题 |
|---|---|
| `对方午休时间是中午12点到下午2点。` | ✅ 可用 |
| `对方本身是内向话少的人。` | ✅ 可用 |
| `对方会一点厨艺。` | 信息密度过低，检索价值存疑 |
| `对方自称只是傲娇。` | 记录「用户说了什么」，不是「什么是真的」 |
| `对方提到已经过了三天，并因自己太忙而道歉。` | 同上，元评论 |
| `对方提到的那个任务还没确定，估计还得讨论。` | **无指代**，「那个任务」指向不明 |
| `对方想知道伴侣是否会做糖醋排骨` | **问句**被存成 `preference` |
| `用户称助手为其女朋友…` / `对方希望AI扮演其女朋友…` | 见第 2 项（角色指令 + 重复） |

两个结构性原因：

1. **元框架未被禁止**。「对方提到/自称/表示」记录的是用户的言语行为，不是事实。
2. **提取只喂单条消息**。`extract_from_text(text)` 的入参只有本条用户消息，
   没有对话历史，所以「那个任务」这类指代**在原理上无法消解**。

### 待决策

- [ ] `MEMORY_SUMMARY_PROMPT` 禁止元框架（「对方提到/自称/表示/觉得」），
      要求直接陈述事实本身。
- [ ] **给提取喂上下文**（最近 N 轮），让指代可消解。改动较大，涉及
      `settle_memory` 签名与两个调用点。
- [ ] 消解不了指代时判 `is_memory=false` 不存（保守丢弃）。
      **建议采纳**，宁可少存不可存错。
- [ ] 提取率 7% 是否偏低？可能与判据「When unsure, FALSE」过保守有关，
      需与第 6 项（不可见）一起观察，暂不单独调整。

## 5. P1 · 去重阈值过松，同一事实存了多遍

### 证据

第 2 项那对角色记忆 cos=0.756（L2 0.699）被判为不同事实，双双落库。

`MEMORY_DEDUP_THRESHOLD=0.25`，过滤条件 `distance <= threshold`
（`backend/src/core/memory/mod.rs:195`），同样是 L2 距离，
0.25 只拦近乎逐字相同（cos≈0.969）。

`self_profile` 那边 21 行可能也存在同义项并存（未逐条核验）。

### 待决策

- [ ] `MEMORY_DEDUP_THRESHOLD` 提到 **0.7 左右**（cos≈0.76）。数值待实测校准。
- [ ] 去重时若语义相同但 `tier`/`expires_at` 不同，保留哪个？
      现逻辑是无脑 `touch` 旧的。**建议保留信息量更大的那条**（core > intent > short），
      并把 TTL 取最长。改动涉及 `touch` 调用点。

## 6. P1 · 记忆对用户完全不可见

### 现象

LLM 在替用户写永久断言，用户既看不到也无法纠正。

### 证据

`backend/src/api/` 只有两个路由（`chat.rs:22-23`）：

```rust
.route("/chat/stream", post(handle_chat_stream))
.route("/ws", get(handle_ws))
```

**没有任何记忆的查询 / 编辑 / 删除接口。** 而库里躺着
`对方自称只是傲娇`、`用户称助手为其女朋友` 这类断言。

这可能是「记忆感觉伪」的最大来源 —— 不是它记错了，而是这一切**无法验证**。

### 待决策

- [ ] 是否做记忆管理接口 + 前端页（`GET /memories`、`PATCH`、`DELETE /memories/:id`）。
- [ ] 若做，是否需要「低置信度记忆待确认」机制（LLM 标记 → 用户确认 → 转正）。
      这会与第 2 项的「profile 自动演进」共用一套确认流程。
- [ ] 优先级建议排在第 1、2 项**之后**：先让记忆准，再让它可见。反过来做意义不大。

## 7. P1 · `settle_memory` 耦合在「发送成功」之后

### 现象

出站发送失败时，跳过的 `else` 分支里装着 `settle_memory`，
**该轮对话的记忆不会沉淀**。LLM token 已消耗、`messages` 表已写入，
但用户没收到、记忆库也没有这条内容。恢复只能靠用户重发触发新一轮 LLM。

代码位置：`backend/src/channels/telegram.rs:413`、`backend/src/channels/ilink/mod.rs:282`。

> 已在「出站重试」改动中大幅缓解（失败前会重试 5 次、约 13 秒窗口），
> 但耦合本身仍在：重试耗尽依然丢记忆。

### 待决策

- [ ] 把 `settle_memory` 与发送解耦：移到发送**之前**，或独立于发送结果。
      **建议移到发送之前** —— 记忆是内部状态，不应取决于外部投递是否成功。
- [ ] 或配套做 outbox（见第 8 项），从根上解决。

## 8. P2 · 出站在途消息无持久化重投

### 现象

进程崩溃时在途的那条消息永久丢失。无 outbox / 待发表（`schema.rs` 的业务表不含消息可靠投递表），
无重试队列。

入站方向**是有保障的**（游标先落盘再处理，崩溃重启续传），
出站方向完全相反 —— 两侧不对称。

### 待决策

- [ ] 是否做 `pending_sends` 表 + 启动时扫表重投。
      与第 7 项一并决策，做了就同时解决两者。
- [ ] 代价：新增 schema 版本、启动时序、幂等键设计。**成本明显高于第 7 项的解耦方案**，
      建议先做解耦，outbox 视实际丢失频率再定。

## 9. P2 · iLink 主动推送失败会烧掉用户的 context_token

- [ ] 或区分失败原因：网络类失败不丢，`context_token 已过窗口` 才丢。

## 10. P2 · 意图判定拿不到当前时间（用户已决定暂不动）

### 现象

模型在「夜还长」这类描述上会编造时间。表现为回复与真实时段不符。

### 结论（已查清，非时区 bug）

- 本机时区 `+08:00`，`16:37` 与 `UTC 08:37` 对齐，时区无误。
- 真正原因：`speak::decide()` **完全没有收到当前时间**，模型无从得知。
  `local_hour` 未被使用，`phase_of` 生产路径未接。
- 通道层也不传：`history_text()` 与召回文本均不带时间戳。

### 已决策

> 用户明确「暂时不动」意图提示的时区修复。
> 高风险 prompt 重排与服务端 prefix cache 一并暂缓。

## 11. P2 · provider prompt cache 未做

`system_prompt` 每轮重算重拼，人设块 + 能力段 + 少量静态尾部。

- **未做原因**：与第 10 项的 prompt 重排耦合，且改动风险高于收益。
- **已决策**：随第 10 项一并暂缓。

> 本轮已完成的低风险优化中，`Profile::block()` 增加了 10 秒 TTL 缓存，
> 已消除每轮持全局 DB 锁查询 `self_profile` 的开销（见 `docs/architecture.md`）。

## 附录 B · 复现方式

诊断脚本（只读，不改库）在 `%TEMP%\opencode\`：

| 脚本 | 用途 |
|---|---|
| `memdiag.py` | 记忆全文、分布、过期统计 |
| `recalldiag.py` | 用户消息 × 记忆的相似度，验证阈值 |
| `metricdiag.py` | 确认向量已归一化、推导 L2↔余弦关系 |
| `injectdiag.py` | 各阈值下的平均注入条数、实际注入内容 |
| `overlap.py` | `self_profile` 与 `memories` 的角色类重叠 |

`metricdiag.py` 需本地 embedding 端点（`EMBEDDING_API_URL`，当前为 LM Studio）。

**注意**：第 1 项的结论依赖「阈值单位是 L2 距离」这个前提。
若 `vec0` 建表将来显式指定了 `distance_metric`，或 embedding 模型换成未归一化输出，
上述换算全部失效，需重测。

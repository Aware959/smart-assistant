# AI 自我演化与多 Agent 体系需求分析

> 状态：MVP 方向与首批边界已确认；身份契约、v22 持久化、版本化渲染、角色工具边界、
> 显式缓存失效、提案校验/限流/人工审批、后台提案生成、事务应用与回滚闭环均已实现。
> 后台演化默认关闭，只在 `sa-link` 中按周期运行。
> 日期：2026-10-29（初稿 2026-10-27）。  
> 适用范围：`smart-assistant` 当前 Telegram 主线；共享代码可演进，但不主动改 Web / iLink。  
> 关联文档：`docs/architecture.md`、`docs/archive/agent-tool-loop-architecture-review.md`。

---

## 0. 结论先行

这个方向值得做，但要把“AI 可以随意改写自己的 system prompt”改造成
**有边界的自我人格演化**：

1. **不要让模型直接编辑不可信的 system prompt 原文**。  
   人设应拆成结构化的自我属性，system prompt 由“不可变平台契约 + 当前身份快照 +
   会话状态”动态渲染。

2. **先建身份模型，再做自动演化**。  
   没有稳定的字段、版本、可见范围和审批规则，所谓“自我演化”只会变成不可审计的
   提示词漂移。

3. **演化不是每次聊天时顺手改自己**。  
   对话 Agent 负责聊天；身份演化应是独立的后台/反思流程，产出提案，经过校验、
   审批和事务提交后才生效。

4. **需要拆多 Agent 角色，但不需要立刻造通用 Agent 框架**。  
   先把“对话”“主动开口”“身份演化”拆成职责清晰、工具白名单不同的角色，共享
   LLM、Profile、Memory、Sessions、DB 等底层服务即可。

5. **MVP 推荐顺序**：  
   身份模型与渲染层 → Agent 角色/工具边界 → 身份变更提案 → 人工确认/审计/回滚 →
   再评估低风险自动生效。

“更像人”不应等同于“拥有无限自修改权限”。更接近人的部分是：
**连续的身份感、会受经历影响、变化有惯性、能解释自己的变化，也仍然受现实边界约束。**

## 1. 背景与问题

### 1.1 当前目标

当前 AI 的行为主要由系统提示词和人设控制，且这部分基本不可变：

- 系统提示词模板在代码里；
- 人设来自 `self_profile`；
- 两条对话路径都把渲染后的人设注入提示词；
- LLM 没有修改自己人设的运行时入口。

用户希望探索：

> 在注入系统提示词和人设之后，让 AI 从自己的视角决定“我要如何改变”，
> 从而获得更大的自由度，是否能让它更像人？

### 1.2 真正要解决的不是“改字符串”

“让模型改写 system prompt”只是实现手段，需求本身应拆成四个问题：

1. AI 的哪些部分可以被经历影响？
2. 变化如何被表达、存储、验证和回滚？
3. 谁有权批准变化，用户如何看见变化？
4. 演化行为如何与正常聊天、主动开口隔离，避免一个 Agent 越来越膨胀？

### 1.3 当前已经出现的信号

当前实际存在两套业务行为：

- **对话 Agent**：`Agent::chat_stream`，负责回复用户。
- **主动开口 Agent**：`Agent::proactive_stream`，由 `core/intent/` 定时触发，负责判断是否主动联系。

两者已经使用不同提示词和不同工具集，但仍共用同一个 `run_tool_loop`。
这说明“角色分化”已经发生，只是运行时还没有被显式建模。再加入身份演化后，
如果继续把分支塞进同一个循环，复杂度和工具权限风险都会快速上升。

## 2. 当前实现事实

本节只记录代码现状，不代表最终设计。

| 项目 | 当前事实 |
|---|---|
| 人设存储 | `backend/src/db/self_profile.rs` 维护 `self_profile(key, value, updated_at)` KV 表 |
| 人设读取 | `backend/src/core/self_profile.rs::Profile::snapshot()` 优先按最新身份版本渲染 canonical 字段；无版本记录时兼容旧 KV 插入序，带 10 秒 TTL 缓存 |
| 提示词注入 | `backend/src/core/context/prompt.rs::persona_block()` 将人设作为最高优先级稳定人格注入 |
| 对话提示词 | `system_prompt(profile)`：共享基底 + 对话示例 + 输出约定 |
| 主动提示词 | `proactive_system_prompt(profile)`：共享基底 + 主动沉默规则 + 输出约定 |
| 人设写入 | `db::self_profile::set/delete` 已实现，但当前无业务调用，注释标明为 AI 自我演化预留 |
| 对话工具 | `send_message`、`send_dice`、`send_sticker`、`generate_image`、`generate_voice`、`get_now`、`recall_memory`、`remember`（媒体工具受配置开关控制） |
| 主动工具 | `send_message`、`get_now`、`recall_memory`，刻意不含 `remember` |
| 工具循环 | 对话和主动路径共用 `Agent::run_tool_loop`，用 `ToolPolicy` 区分“必须回复”和“可以沉默” |
| 主动触发 | 仅 `sa-link` 启动，受 `INTENT_ENABLED` 控制，默认关闭 |
| 版本与审计 | v22 已有 `identity_change_proposals` / `self_profile_versions`；提案校验、限流、审批、事务应用、版本回滚和 Telegram 管理命令均已接入，审批人与版本操作者写入审计 |
| 记忆边界 | 用户事实在 `memories`；AI 自我属性在 `self_profile`；两者不应重新混合 |

关键结论：

- 当前并不存在“一个可被 AI 直接改写的 system prompt 变量”；
- 系统提示词是代码模板，`self_profile` 只是被注入的结构化人设；
- 因此，功能不应从“给模型一个改写 prompt 的工具”开始，而应从“定义可演化的身份模型”开始。

## 3. 需求边界

### 3.1 分层模型

建议把影响 AI 行为的内容拆成以下层级：

```text
L0 平台契约（不可变）
  ├─ 安全、隐私、权限、工具能力边界
  ├─ 身份披露、审批和系统规则
  └─ 不允许由 AI 自我演化修改

L1 AI 身份模型（可演化，但受 schema 与规则约束）
  ├─ 自我概念 / 人格
  ├─ 价值观与立场
  ├─ 表达风格
  ├─ 兴趣与偏好
  └─ 关系姿态

L2 由身份模型生成的 persona prompt（派生，不手工编辑）

L3 当前状态（短期）
  ├─ 当前情绪、精力、当下话题
  └─ 应有 TTL 或按会话重置，不应自动写成永久人格

L4 用户记忆（独立）
  └─ 关于用户的事实、偏好、经历和约定；不与 AI 自我属性混存
```

### 3.2 建议允许演化的内容

以下只是候选字段，最终字段需要拍板：

| 字段类别 | 例子 | 风险 | 建议 |
|---|---|---|---|
| 自我概念 | “我是谁”“我如何看待自己” | 中 | 允许提案，MVP 人工确认 |
| 性格与价值观 | 更主动 / 更克制、重视什么 | 高 | 必须限制幅度并可回滚 |
| 表达偏好 | 句子长短、语气、称呼习惯 | 低 | 可作为首批自动演化候选 |
| 兴趣与偏好 | 喜欢的话题、日常选择 | 低 | 可演化，但要有来源证据 |
| 关系姿态 | 亲近程度、撒娇/克制、边界感 | 中高 | 需要用户明确同意，不能单向加深依赖 |
| 当前情绪 | 今天低落 / 兴奋 | 低（短期） | 放 L3，不作为永久人格 |

### 3.3 不建议开放的内容

- 任意 system prompt 原文；
- 工具权限、工具白名单、审批策略；
- 安全、隐私、平台契约；
- 代码、配置、数据库 schema；
- 对其他用户或外部系统的权限；
- 无审计、无回滚、无频率限制的批量人格重写。

### 3.4 “更像人”的验收标准

不能只用主观感觉判断。建议至少观察：

- 人设前后是否连贯，而不是每次对话换一个人；
- 变化是否能被具体经历解释，而不是随机漂移；
- 变化后是否仍遵守平台边界；
- 用户是否能看见、拒绝、回滚关键变化；
- 变化是否降低重复解释、人格矛盾和记忆冲突；
- 是否出现过度迎合、依赖诱导、身份混乱等负面行为。

## 4. 身份模型

### 4.1 为什么先做身份模型

身份演化必须先回答“改什么、改成什么算合法”。如果直接让 LLM 写一段新的
system prompt：

- 无法知道改变了哪些字段；
- 无法做字段级审批；
- 无法做版本比较和回滚；
- 无法限制单次变化幅度；
- 无法区分人设、当前状态和用户记忆。

所以推荐先建立正式的 `AgentIdentity` 领域模型，再实现自动演化。

### 4.2 最小身份契约

候选结构（实现语言与数据库细节待定）：

```text
AgentIdentity
  - version
  - fields: Map<IdentityFieldKey, IdentityFieldValue>
  - updated_at

IdentityField
  - key（白名单枚举）
  - value（有长度、格式和内容限制）
  - mutability（immutable / approval_required / low_risk）
  - description
```

推荐的首批字段：

- `self_concept`
- `personality`
- `values`
- `voice_style`
- `interests`
- `relationship_stance`

字段必须有：

- 固定 key；
- 最大长度；
- 空值/删除规则；
- 是否允许自动修改；
- 变更是否需要审批；
- 变更是否允许一次改多个字段。

### 4.3 渲染与缓存

当前 `Profile::snapshot()` 用 10 秒 TTL 处理人工改库后的不一致。自动演化上线后，
不能只依赖 TTL：

- 每次身份变更必须产生新的 `identity_version`；
- 渲染结果应能按版本失效；
- 写入成功后立即让相关缓存失效；
- 提示词中可记录身份版本，便于审计和复现。

### 4.4 身份范围

当前系统更像单用户/单实例场景，`self_profile` 是全局 KV。

MVP 建议明确采用：

- **一个实例只有一个全局 AI 身份**；
- 暂不做“每个用户一套独立人格”；
- 若未来需要多用户，再引入 `identity_scope` 或关系级 profile。

这一点必须显式写清楚，否则后续会在“同一个人格服务多个用户”与
“每个关系独立演化”之间反复摇摆。

## 5. 自我演化流程

### 5.1 推荐流程

```text
触发器
  → 读取当前身份 + 最近对话 / 记忆 / 反思证据
  → Identity Evolution Agent 产出结构化提案
  → 校验（字段、长度、风险、频率、安全边界）
  → 审批（MVP 默认人工确认）
  → 事务提交（更新快照 + 写入版本 + 审计记录）
  → 失效缓存
  → 后续提示词使用新版本
  → 可回滚
```

### 5.2 提案应是结构化数据

不要让模型直接返回一段“新 prompt”。提案至少应包含：

```json
{
  "field": "voice_style",
  "before": "更简短、偶尔用表情",
  "after": "更愿意主动分享自己的看法，但仍然保持短句",
  "reason": "最近多次对话里，用户明确表示喜欢我有自己的观点",
  "evidence_message_ids": ["..."],
  "confidence": "medium",
  "risk": "low"
}
```

提案应说明：

- 改的是哪个字段；
- 为什么现在要改；
- 依据了哪些经历；
- 变化幅度是否过大；
- 是否与既有价值观或用户边界冲突。

### 5.3 触发时机

候选触发方式：

- 会话结束后异步反思；
- 每日/每周低频后台任务；
- 累计一定数量新经历后触发；
- 用户显式说“你可以记住/改变这个”。

不建议：

- 在每轮正常回复中顺手修改人格；
- 在用户等待回复的关键路径上做深度自我反思；
- 同一轮对话中刚被批评就立刻大幅改写人格。

频率上限必须先定。具体数值（每天、每周最多几次）属于开放决策。

### 5.4 审批与生效

候选策略：

| 策略 | 说明 | 风险 |
|---|---|---|
| 全部人工确认 | 每个提案由用户批准 | 最安全，MVP 推荐 |
| 按风险分级 | 低风险自动，高风险的确认 | 体验好，但需要可靠的风险分类 |
| 全部自动可回滚 | AI 自主提交，保留审计与回滚 | 自由度最高，风险也最高 |

MVP 建议从“全部人工确认”开始。可以先生成提案但暂不提供自动应用。

### 5.5 回滚与删除

- 每次生效必须保留完整 before/after 快照；
- 支持按版本回滚；
- 默认禁止自动删除核心身份字段；
- 删除字段、清空人格、批量重写必须走人工确认；
- 回滚本身也要写审计记录。

### 5.6 频率、幅度与冷却

需要明确限制：

- 单次最多修改几个字段；
- 单字段单次最大变化幅度；
- 同一字段两次修改的最小间隔；
- 全局每日/每周变更次数；
- 发生用户纠正、冲突或敏感事件后的冷却期。

这些限制应放在代码和数据库约束里，而不是只写在提示词里。

## 6. 多 Agent 体系

### 6.1 结论

应该拆角色，但不必马上引入通用多 Agent 框架。

当前 `run_tool_loop` 可以继续作为**底层执行机制**，但不应继续承载越来越多
业务语义。业务角色应各自拥有：

- 自己的提示词构建；
- 自己的工具白名单；
- 自己的输入/输出契约；
- 自己的终止策略；
- 自己的频率、预算和审计字段。

### 6.2 推荐角色

#### Conversation Agent

职责：

- 正常接待用户消息；
- 读取身份与会话历史；
- 通过工具发送文本、表情、媒体；
- 按需召回记忆、写入用户记忆。

特点：

- 面向用户；
- 必须有回复或明确失败；
- 可以使用输出工具和记忆工具。

#### Proactive Agent

职责：

- 根据时间线和频率门槛判断是否主动开口；
- 默认沉默；
- 需要时可以发送一条或少量消息。

特点：

- 不写用户记忆；
- 不修改身份；
- 不能因为“想主动联系”而获得身份演化权限。

#### Identity Evolution Agent

职责：

- 在后台读取经历、对话、记忆和当前身份；
- 生成结构化身份变更提案；
- 不直接对用户说话；
- 不直接修改用户记忆或平台配置；
- 只有在审批通过后由独立执行路径写入。

特点：

- 低频率、可异步、可离线；
- 工具以只读证据和提案为主；
- 模型可以比对话模型更强，但必须受 schema 约束；
- 所有提案和结果可审计。

#### Memory Curator Agent（候选，非 MVP）

当前 `remember` 由对话 Agent 在工具循环里执行。未来如果记忆写入质量成为问题，
可以把“用户记忆整理”拆成独立后台角色。

暂不建议现在就拆，因为：

- 当前记忆边界刚刚稳定；
- 身份演化比记忆整理更依赖多 Agent 边界；
- 先拆会扩大本次需求范围。

### 6.3 工具权限矩阵

以下是候选矩阵，最终工具名可在实现时调整：

| 能力 | Conversation | Proactive | Identity Evolution |
|---|---:|---:|---:|
| 发送用户消息 | 是 | 是 | 否 |
| 媒体/骰子/贴纸 | 是 | 否（当前） | 否 |
| `get_now` | 是 | 是 | 是（只读） |
| `recall_memory` | 是 | 是 | 是（只读） |
| `remember` | 是 | 否 | 否 |
| 读取身份 | 是（自动注入） | 是（自动注入） | 是 |
| 提交身份提案 | 否 | 否 | 是 |
| 直接应用身份变更 | 否 | 否 | 否（由审批执行器负责） |
| 修改工具权限/平台契约 | 否 | 否 | 否 |

### 6.4 运行时结构建议

不需要把现有 `Agent` 一次性推倒重写。推荐演化路径：

```text
现有 Agent
  → 抽出通用 LLM 调用 / 工具执行 / 消息配对机制
  → 为每个角色提供独立 prompt builder、tool policy、输出 schema
  → 业务入口只依赖角色端口，不依赖一个不断膨胀的 Agent 方法集合
```

候选模块方向（名称仅作示意）：

```text
core/agents/conversation
core/agents/proactive
core/agents/identity_evolution
core/agent_runtime
```

重点是职责边界，不是目录名字。不要为了“像框架”而提前造一层通用编排器。

## 7. 数据模型候选

以下设计的持久化部分已落地到 v22：提案表、版本审计表及对应 DAO 已实现；提案
校验、限流、审批、事务应用与回滚由 `IdentityService` 负责。

### 7.1 保留 `self_profile` 作为当前快照

`self_profile` 继续服务高频读取和提示词渲染，但写入必须经过身份服务，
不能让普通 Agent 或任意工具直接写 DAO。

### 7.2 新增 `identity_change_proposals`

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 提案 id |
| `field_key` | 目标身份字段 |
| `before_value` | 提交前值 |
| `after_value` | 提案后值 |
| `reason` | 为什么改变 |
| `evidence` | 证据，可为消息 id / 记忆 id / 摘要 |
| `confidence` | 模型置信度或规则评估 |
| `risk_level` | low / medium / high |
| `status` | pending / approved / rejected / applied / rolled_back |
| `proposer` | 产生提案的 Agent / 模型 / 版本 |
| `decided_by` | 审批操作者；MVP 为 `telegram:<chat_id>`，旧行为空 |
| `created_at` | 创建时间 |
| `decided_at` | 审批时间 |
| `applied_at` | 生效时间 |
| `rolled_back_at` | 回滚时间 |

### 7.3 新增身份版本或审计记录

`self_profile_versions` 候选字段：

- `version`（单调递增）；
- `snapshot`（完整快照或变更后的快照）；
- `change_id` / `proposal_id`；
- `source`（manual / evolution_agent / rollback）；
- `reason`；
- `operator`（写入该版本的审批人或回滚操作者）；
- `created_at`；
- `rolled_back_from`。

要求：

- 生效写入与版本记录在同一事务中完成；
- 任何自动写入都必须能追溯到提案；
- 人工改库不能成为长期常态，后续应通过管理入口完成。

### 7.4 身份版本和缓存

- 读取路径可缓存，但缓存 key 应包含身份版本；
- 写入成功后主动失效，而不是等待 10 秒 TTL；
- 日志记录本轮使用的身份版本；
- 回滚后同样立即失效。

## 8. 开源项目参考

目标不是把别的框架搬进来，而是借用已经被验证的模式，避免重新发明。

### 8.1 Letta / MemGPT：最直接可借鉴

Letta（前身 MemGPT）把上下文拆成 memory blocks：

- `persona`：AI 自己的自我概念、性格和行为准则；
- `human`：关于用户的信息；
- block 有 label、value、大小限制；
- block 可以持久化，并由工具编辑；
- 也可以由多个 Agent 共享。

它验证了“结构化 persona block”比“让模型自由重写整段 system prompt”更可控。

更重要的是 Letta 的 **sleep-time agent**：

- 主对话 Agent 不拥有编辑 core memory 的工具；
- 后台 sleep-time agent 负责整理和修改；
- 两个 Agent 可以使用不同模型、不同频率；
- 记忆编辑异步发生，不阻塞正常对话。

这与本需求的推荐方向高度一致：身份演化应是独立后台角色，而不是对话 Agent 的
第 9 个工具。

参考：

- https://www.letta.com/blog/memory-blocks/
- https://www.letta.com/blog/sleep-time-compute/

### 8.2 OpenAI Agents SDK：借鉴角色边界

OpenAI Agents SDK 区分：

- agents as tools：主管 Agent 保持控制，调用专家完成有限子任务；
- handoffs：把当前轮交给专家 Agent；
- guardrails：输入/输出校验；
- 专家 Agent 拥有自己的提示词和工具。

可借鉴的是“专家角色而不是一个万能 Agent”，而不是把整个 SDK 引入本项目。

参考：

- https://openai.github.io/openai-agents-python/multi_agent/

### 8.3 LangGraph Supervisor：借鉴显式编排

LangGraph 的 supervisor 模式用中心节点协调多个专家 Agent，适合流程明确、
需要状态图的系统。

本项目当前规模不需要引入图编排框架；但可以借鉴：

- 角色之间由代码明确路由；
- 每个专家有独立职责；
- 状态转换可观察、可测试。

参考：

- https://github.com/langchain-ai/langgraph-supervisor-py

### 8.4 Voyager：借鉴“演化外部资产”

Voyager 的自我改进重点是技能库：通过执行反馈、错误和自我验证不断积累可复用技能，
而不是无限改写核心运行时。

对本项目的启发：

- 优先演化有结构、可验证、可回滚的外部资产；
- 不要一开始就允许改写平台契约或工具权限；
- 身份变化也应该是“有 schema 的资产变化”，不是任意文本替换。

参考：

- https://github.com/MineDojo/Voyager

### 8.5 Generative Agents：借鉴反思，不照搬模拟

Generative Agents 用 memory stream、reflection 和 planning 让角色从经历中形成更高层
认知。它适合“从对话中提炼变化依据”的反思阶段，但其完整模拟世界、地图和日程系统
不适合直接搬入当前项目。

参考：

- https://github.com/pauljCherian/generative-agents

### 8.6 借鉴结论

| 需求 | 借鉴对象 | 本项目的采用方式 |
|---|---|---|
| 结构化自我属性 | Letta memory blocks | 保留并强化 `self_profile`，加字段白名单 |
| 后台整理身份 | Letta sleep-time agent | 独立 Identity Evolution Agent |
| 角色边界 | OpenAI Agents SDK | 不同角色独立 prompt/tool policy |
| 显式角色编排 | LangGraph supervisor | 先用代码路由，不引入图框架 |
| 可验证的自我改进 | Voyager | 提案先结构化、再验证、再应用 |
| 从经历反思 | Generative Agents | 只借鉴 reflection，不搬整套模拟环境 |

## 9. 非目标

本方案明确不包含：

- 修改 Web / iLink 端；
- 给模型任意改写 system prompt 的能力；
- 让模型修改工具权限、审批规则或平台安全边界；
- 实现通用多 Agent 编排平台；
- 把用户记忆并入 AI 人格；
- 在正常回复路径中自动、频繁、无审计地重写人格；
- 在没有版本、回滚和可见性的情况下开启自动演化。

## 10. 已确认决策（2026-10-29）

以下结论已由用户确认，MVP 编码以此为准：

| 决策项 | 结论 |
|---|---|
| 身份范围 | 单实例一套全局 AI 身份；MVP 不做按用户/关系的人格隔离 |
| 首批字段 | `self_concept` / `personality` / `values` / `voice_style` / `interests` / `relationship_stance` 六个 canonical 字段；旧中文 key 通过 alias 兼容 |
| 审批策略 | 六个字段全部只允许“提案 + 人工批准”，MVP 不做低风险自动生效 |
| 高风险字段 | `self_concept` / `values` / `relationship_stance` 必须人工批准；关系姿态还要求用户明确同意 |
| 用户入口 | 首版只做 Telegram 管理命令；不做 Web 管理页 |
| 触发方式 | `sa-link` 后台低频任务，默认关闭；每天最多 1 次、最多 3 条待审提案、同一字段 7 天冷却 |
| 情绪/精力 | 属于 L3 短期状态，不写入永久身份；MVP 不做 |
| Memory Curator | 本次不拆分，`remember` 继续留在对话 Agent |
| 评估方式 | MVP 持久化提案状态、审批人、时间戳与版本来源，可通过这些审计数据推导通过率 / 拒绝率 / 回滚率；人格一致性与越界行为暂靠人工抽查，不建离线评测集 |

身份契约已按上述结论落地于 `backend/src/core/identity.rs`：字段白名单、长度限制、
控制字符拒绝、旧 key alias 映射、关系姿态明确同意标记和 canonical 渲染顺序均已固定。
`Profile::snapshot()` 已按最新身份版本渲染，并在无版本或快照损坏时兼容回退旧 KV。
`IdentityService` 已实现提案创建、真实消息证据校验、风险推导、全局每日限流、
单字段 7 天冷却、最多 3 条 pending 提案，以及 `pending -> approved/rejected`
的人工审批。批准后的 `approve_and_apply` 在单个 SQLite 事务内更新
`self_profile`、写入完整快照版本、推进提案状态，提交后立即失效 `Profile` 缓存；
`rollback` 撤销最新 applied 提案，`rollback <version>` 可恢复任意更早的已审计快照，
两者都会追加 rollback 版本，不删除历史。审批人写入提案 `decided_by`，应用 / 回滚
操作者写入版本 `operator`；Telegram 身份管理命令仅允许 `TELEGRAM_ALLOWED_IDS`
内的会话使用（白名单留空时为单人部署兼容模式，仍可操作）。

后台 `IdentityEvolutionAgent` 已接入 `sa-link`：`IDENTITY_EVOLUTION_ENABLED=1`
才启动，首次运行前等待 `IDENTITY_EVOLUTION_INTERVAL_HOURS`（默认 24 小时）；
证据来自已映射会话的最近消息、长期记忆与当前身份。模型只能产出六字段结构化
提案，不能发送消息、写用户记忆、直接应用身份或修改工具权限。

## 11. MVP 与验收标准

### MVP 范围

1. 建立正式的 `AgentIdentity` 模型；
2. 将现有 `self_profile` 渲染纳入明确的身份 schema；
3. 明确 Conversation / Proactive / Identity Evolution 三个角色的工具白名单；
4. 支持后台生成结构化身份变更提案；
5. 支持人工确认后事务性应用；
6. 支持版本记录、审计和回滚；
7. 明确全局身份范围，不引入多用户人格隔离。

### 验收标准

- 现有 `self_profile` 数据渲染结果可兼容迁移；
- 普通对话和主动开口的现有行为不发生非预期变化；
- 身份演化角色无法直接发消息给用户；
- 身份演化角色无法修改工具权限、安全边界或任意 system prompt；
- 每个生效变化都能追溯到提案、证据和操作者；
- 回滚后下一次提示词读取立即使用旧版本；
- 相关模块有单元测试，验证字段白名单、长度限制、审批状态和回滚；
- 文档明确哪些是已实现，哪些仍是候选设计。

## 12. 任务拆分草案

以下任务表保留为交付追踪；MVP 已完成 T1-T7，T8 明确不做。T4 的“通用执行机制抽取”
没有另造通用编排器：现有 `run_tool_loop` 继续作为对话 / 主动的共享底层，身份演化
走独立的结构化 LLM 调用；三角色边界由代码白名单与派发校验固定。

| ID | 阶段 | 任务 | 依赖 | 验收 |
|---|---|---|---|---|
| T1 | 设计 | 拍板身份范围、字段清单、审批策略和触发频率 | 无 | 本文件相关待决策项有明确结论 |
| T2 | 身份 | 定义 `AgentIdentity`、字段白名单、限制和错误类型 | T1 | 单测覆盖合法/非法字段和边界 |

| T4 | Agent | 抽出可复用的 LLM/工具执行机制，定义三个角色的 prompt/tool policy | T1、T3 | 对话/主动现有行为通过回归测试；身份角色无发送工具 |
| T5 | 提案 | 新增提案数据结构与持久化，不直接修改 `self_profile` | T2、T4 | 提案可查询、可审计，状态机可测试 |
| T6 | 演化 | 实现后台 Identity Evolution Agent，读取证据并产出提案 | T5 | 不发送用户消息，不直接写入当前身份 |

不要先做 T6 再补身份模型，否则会在一个不稳定的文本结构上叠加自动写入。

## 13. 现阶段结论

这条线可以作为 `smart-assistant` 的长期方向，但当前第一步不是“让 AI 改提示词”，
而是先把身份、状态、记忆和多 Agent 职责拆清楚。

近期最稳妥的落地方式是：

- 先把本文件作为需求基线；
- 拍板第 10 节的开放问题；
- 按第 12 节从身份模型开始拆任务；
- 在身份模型稳定前，不开放任何自动写入 `self_profile` 的生产路径。
